Physical operators, and the pull they answer to.

§ 01Plans are not programs

By the end of chapter 4 you had a logical plan: a small tree of nodes that says what the query wants. Filter sits above Scan, Project sits above Filter, and none of them say a single word about how any of it will actually happen. That vagueness is deliberate. A logical plan is a claim about results; it is not yet a claim about work.

A physical operator is where the claim gets paid for. Same shape of tree, but every node now commits to a strategy — this filter evaluates a compiled predicate, that join builds a hash table on the left input, this scan reads a column slice rather than whole rows. The tree looks similar enough that people confuse the two for weeks. The difference is that you can cost a physical plan and you cannot cost a logical one.

§ 02The operator contract

Almost every engine written since System R agrees on the same tiny interface, usually called the Volcano or iterator model. An operator exposes one method — give me the next row, or tell me you are finished — and it may call that same method on its children as many times as it likes.

The consequence is worth stating plainly: no operator ever knows how big its input is. It cannot, because its input has not been produced yet. Rows are pulled through the tree one at a time from the top, and memory stays flat no matter how large the table is.

src/exec/operator.tsTypeScript
// The whole contract. Everything else is an implementation of it.
interface Operator<Row> {
  open():  void;
  next():  Row | null;   // null == exhausted
  close(): void;
}

class Filter<Row> implements Operator<Row> {
  constructor(
    private input: Operator<Row>,
    private pred: (r: Row) => boolean,
  ) {}

  open()  { this.input.open(); }
  close() { this.input.close(); }

  next(): Row | null {
    let r: Row | null;
    while ((r = this.input.next()) !== null) {
      if (this.pred(r)) return r;
    }
    return null;
  }
}
Worth noticing Filter has no buffer, no array, and no length. It is pure control flow over somebody else's rows — which is exactly why you can stack forty of them without thinking about memory.

Notice what did not happen: at no point did the pipeline hold more than one row. Swap scan(rows) for a generator over a four-gigabyte file and every line above still works unchanged. That property — not speed — is the reason the iterator model outlived nearly everything it competed with.

§ 04Materialise, then stop

The version most people write first builds an array at every stage. It is easier to debug and it is fine at ten rows, but it allocates the entire intermediate result three times before returning anything at all. Flip the toggle below to watch it collapse into the pull-based form.

Materialised → streaming 3 allocations removed
1const a = rows.slice(); // copy 1
2const b = a.filter(hot); // copy 2
3const out = b.map(r => pick(r, cols)); // copy 3
4
5for (const r of out) emit(r);
6
7// peak memory: O(n) — three times over
1const plan = project(
2 filter(scan(rows), hot),
3 cols,
4);
5let r;
6while ((r = plan()) !== null) emit(r);
7// peak memory: O(1)
Same rows, same order, same predicate. The only thing that changed is when the work happens.

The streaming version is not automatically faster — for tiny inputs the array version wins, because Array.prototype.filter is a tight loop in C++ and your closure chain is not. It wins on shape: memory stops depending on input size, and the first row arrives before the last row is read. Those two properties are what let a LIMIT 10 finish in microseconds on a table with a hundred million rows.

§ 05What to build next

Three operators are enough to run real queries, and it is worth stopping here to add them before chapter 6 hands you an execution loop that assumes they exist. In rough order of how much you will learn per line written:

Limit — trivial, and the first operator that returns null while its child still has rows. Sort — the first one that genuinely must materialise, which makes it the honest counterexample to everything above. HashAggregate — builds a map in open(), drains it in next(), and will teach you more about operator lifecycle than any amount of reading.

Chapter 6 wires these into a single execution loop and measures where the time actually goes — which, in a pull-based engine, is almost never where you expect.
